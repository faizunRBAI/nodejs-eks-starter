# nodejs-eks-starter

A Node.js/Express REST API running on Amazon EKS, provisioned by Terraform and
shipped by a security-gated GitHub Actions pipeline. Ships with a full CRUD
`/api/items` resource backed by RDS Postgres, health and readiness probes, and
a rolling-deploy migration mechanism.

> Built from the UDAP `nodejs-eks` production blueprint. The long-form
> description of the platform lives in
> [.udap/docs/README.md](.udap/docs/README.md).

## Layout

| Path | What it holds |
|---|---|
| `src/app.js` | Express routes: `/health`, `/ready`, `/api/info`, `/api/items` CRUD |
| `src/server.js` | HTTP server with graceful SIGTERM shutdown |
| `src/db.js` | pg Pool singleton (sslmode=require, pool size 5) |
| `bin/migrate` | Plain-SQL migration runner (node script) |
| `db/migrations/` | Numbered SQL migrations, applied once each before every release |
| `public/` | Operator page served at `/` |
| `test/` | Unit tests (Jest + supertest, pg pool mocked) |
| `infra/` | All Terraform: VPC, EKS, node group, ECR, KMS, RDS |
| `k8s/` | Deployment, Service, HPA, PodDisruptionBudget, ServiceAccount, migration Job |
| `.udap/architecture.d2` | Architecture diagram (UDAP D2 profile) |
| `.udap/pipeline.yaml` | Pipeline spec — CI workflow files are rendered from it |

## Endpoints

| Route | Method | Purpose |
|---|---|---|
| `/` | GET | Operator page with live status |
| `/health` | GET | Liveness — never touches the database |
| `/ready` | GET | Readiness — pings Postgres when configured |
| `/api/info` | GET | Runtime version and uptime |
| `/api/items` | GET | List all items (newest first) |
| `/api/items` | POST | Create an item `{ "title": "..." }` |
| `/api/items/:id` | GET | Get one item by id |
| `/api/items/:id` | PATCH | Update `title` and/or `done` |
| `/api/items/:id` | DELETE | Delete an item |

## Running it locally

```bash
npm install
npm start                 # http://localhost:3000
```

With a local database (no TLS needed locally):

```bash
DATABASE_URL='postgres://user:password@localhost:5432/appdb' \
NODE_ENV=development npm start
```

Without `DATABASE_URL` the service starts and `/ready` reports
`database: not configured` — useful for testing the application tier alone.

The gates the pipeline runs, in local form:

```bash
npm run lint              # ESLint, zero warnings allowed
npm run format            # Prettier (writes fixes; advisory in CI)
npm test                  # Jest unit tests
docker build -t app .     # the image the pipeline builds
```

## Database migrations

Every deploy runs `node bin/migrate` as a Kubernetes Job **before** the new
Deployment rolls out — the schema is ready before any new pod serves traffic,
and a failed migration stops the deploy.

The runner applies numbered `.sql` files from `db/migrations/` once each, in
filename order, inside a transaction, tracked in a `schema_migrations` table:

```
db/migrations/001_init.sql           # items table (shipped)
db/migrations/002_add_orders.sql     # your next migration
```

To run migrations locally:

```bash
DATABASE_URL='postgres://user:password@localhost:5432/appdb' \
  node bin/migrate
```

Because a rolling update runs old and new pods at the same time, **each
migration must be backward-compatible with the currently running code** — add a
nullable column before deploying the code that writes it; drop the old column in
a later release.

## How a deploy runs

Seven gates run in parallel — coding standards, unit tests, Semgrep SAST,
Gitleaks secret scanning, licence compliance, SBOM generation and Terraform
security scanning. All must pass before any AWS resource is touched. Then:
Terraform applies `infra/`, the image is built, pushed to ECR and Trivy-scanned,
manifests in `k8s/` are applied, the rollout is watched, and the load balancer
is health-checked before the deploy is called green.

The pipeline is defined in `.udap/pipeline.yaml`. Edit it there — never edit
`.github/workflows/*` directly, as the next render overwrites it.

## Configuration

Nothing needs to be set by hand. The platform sets these as repository secrets:

| Secret | Used for |
|---|---|
| `PROJECT_NAME` | Resource prefix, K8s namespace, ECR repo name, Terraform state key |
| `TF_STATE_BUCKET` | Terraform remote state bucket |
| `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY` | Provisioning and cluster access |

The Postgres password is generated by Terraform, stays in the state file, and
reaches the pods only as the `app-database` Kubernetes Secret. No manual secret
management is required.

## Operating it

```bash
# Connect kubectl to the cluster (set after first deploy)
aws eks update-kubeconfig --name "$PROJECT_NAME-eks" --region us-east-1

# Inspect
kubectl get pods -n "$PROJECT_NAME"
kubectl logs -n "$PROJECT_NAME" -l app.kubernetes.io/name=api --tail=100

# Roll back one release
kubectl rollout undo deployment/api -n "$PROJECT_NAME"

# Find the public hostname
kubectl get svc api -n "$PROJECT_NAME" -o jsonpath='{.status.loadBalancer.ingress[0].hostname}'
```
